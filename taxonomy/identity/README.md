# Native identity vocabulary

[`v1/identity-vocabulary.json`](v1/identity-vocabulary.json) is the closed vocabulary that [ADR 0009](../../docs/adr/0009-native-identity-and-provider-aliases.md) makes authoritative for GrooveMap-native identity. It names the eight entity kinds a native identifier can be minted for, the seven external namespaces a provider alias may come from, the three ways an alias can be asserted, and the column set and uniqueness rule of the `provider_aliases` table.

[`v1/identity-vocabulary.schema.json`](v1/identity-vocabulary.schema.json) validates the vocabulary document itself. `just identity` validates that schema as a JSON Schema 2020-12 document, validates the vocabulary against it, and checks the closed sets and the alias contract.

## Identifiers

- Native identifiers are UUID version 7 as specified in RFC 9562, generated by a `uuidv7()` column default in PostgreSQL or by `uuid.uuid7()` in a service. No application-side identifier library is introduced.
- Entity kinds are lowercase snake case. `release`, `master`, `artist`, and `label` are rows of `catalog_items`; `artifact`, `owned_copy`, `collection_snapshot`, and `observation` each have their own table. The four catalog kinds are minted at ingest; the other four are created by or for a user.
- Providers split into two namespace kinds. `discogs`, `musicbrainz`, and `wikidata` are catalogs that assign identifiers; `barcode`, `catalog_number`, `isrc`, and `matrix` are printed or stamped identifier namespaces. Both are aliases for the same reason: they identify an entity without belonging to GrooveMap.
- Alias sources separate what a catalog carried (`catalog`), what a person asserted (`user`), and what a matching heuristic proposed (`inference`). An inferred alias is evidence, never an assertion.

## Alias rules

- A provider identifier is never a primary key. It is a row in `provider_aliases` pointing at a native identifier.
- Uniqueness is on `(provider, entity_kind, external_id)` for the currently valid row. That is what makes lookup-or-create idempotent: select, insert with `ON CONFLICT DO NOTHING`, re-select, and two concurrent writers converge on one native identifier.
- `valid_to` is the only alias column that is not required. An open interval leaves it unset; a provider merge, split, or deletion closes the interval and writes a new row rather than rewriting the old one, so an identifier that was once correct stays auditable.
- A consumer resolving a batch resolves it in one round trip. The shared `common.identity` helper in `groovemap-runtime` offers a bulk resolve because the loaders upsert up to a hundred rows per transaction.

## Vendoring rule

The vocabulary is vendored verbatim, byte for byte, into every repository that mints or resolves native identifiers, beginning with `python-libraries`, `discogs-sql-loader`, `musicbrainz-sql-loader`, and `catalog-api`. A vendored copy sits beside a source record naming the design commit and the SHA-256 of this file, and each repository's check gate fails when the copy's digest differs from that record. Compute the digest from the exact bytes of the file:

```console
shasum -a 256 taxonomy/identity/v1/identity-vocabulary.json
```

`just publication-readiness` prints the same digest as `identity_vocabulary_sha256` next to the catalog and media digests, so consumers can pin a reviewed commit and its vocabularies together.

## Changing the vocabulary

Adding an entity kind, a provider, or an alias source is an additive vocabulary change followed by re-vendoring; it is never a code change in a consumer. Renaming or removing an id, or changing what a column means, is a breaking change and requires a new `vocabulary_version` directory. Contraction of the provider-keyed columns is not a vocabulary change at all: ADR 0009 leaves it to its own decision and its own persistence contract version.
